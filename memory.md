# Memory · Sveska

> **Project-local decisions, gotchas, infra facts.** Distinct from agent-level memory (`~/.claude/projects/.../memory/`) which is cross-project user context. This file is for things specific to building Sveska.

## Locked decisions (do not re-litigate)

- **Stack**: Vite 5 + React 18 + TS strict + Zustand + Dexie + vite-plugin-pwa + react-router-dom v6. Frozen per CLAUDE.md §1.
- **Canvas**: Excalidraw vendored at M5 only. tldraw is **permanently dropped** — no licence exposure.
- **Storage**: Dexie (IndexedDB) is primary. `localStorage` only for the one-time legacy import (notepad.js.org compat). Theme + all prefs go through Dexie `prefs` table.
- **Security gates** enforced from M0: CSP `default-src 'self'`, key-leak scanner in build, 180 KB JS gzip budget. Never weaken.
- **Editor**: native `<textarea>` for M1. CodeMirror 6 only when M3.2 (Markdown mode) needs it.
- **Pre-commit**: `prettier + pnpm typecheck` only. Type-aware ESLint per-file gets killed on Windows; full `pnpm lint` runs in CI instead.
- **Tests**: real timers (fake timers fight Dexie async writes). `test-setup.ts` must call `_resetDbForTests()` which closes the connection AND `Dexie.delete('sveska')` — nulling the singleton alone doesn't drop data.

## Gotchas

- **Hostinger DNS record types differ across siblings**: don't blindly PUT CNAME — read existing type first. `sveska.kineticgain.com` is `ALIAS`; `notepad.kineticgain.com` is `CNAME`. Mixing types triggers HTTP 422 conflict.
- **Hostinger DNS PUT with `overwrite=true`** only replaces records matching name+type. Other siblings are untouched. Verified safe for kineticgain.com (22 subdomains).
- **DNS TTL**: was 3600s on the previous CNAMEs; browsers cache up to 1 hr after a flip. If user reports SSL warning post-DNS-change, it's a stale local cache, not a server problem. Fix: `ipconfig /flushdns` + restart browser, or incognito.
- **Husky pre-commit**: dropped per-file ESLint with type-aware rules — it got killed on Windows (memory/timeout). Pre-commit = `prettier + typecheck`. Full lint runs in CI.
- **Vitest fake timers**: don't combine with Dexie. Fake `setTimeout` blocks the IDB request callbacks. Use real timers + generous `waitFor` timeouts.
- **`fake-indexeddb/auto`**: doesn't reset between tests on its own. Need to `db.close()` + `Dexie.delete('sveska')` + null the singleton each `afterEach`.
- **Windows case-insensitive paths**: `Sveska/` (reference bundle) and `sveska/` (app) collide. App lives outside the reference bundle, such as `C:\Users\<user>\Downloads\sveska-app\`, to avoid this.
- **NS delegation drift (2026-05-17)**: `sveska.studio` started delegating to `dns1.p07.nsone.net` / `dns2.p07.nsone.net` (NS1 / Netlify-DNS nameservers) — but **no zone existed there**, so public resolvers got `SERVFAIL` and browsers showed `DNS_PROBE_FINISHED_NXDOMAIN`. The Hostinger zone records were intact. Fix: `PUT /api/domains/v1/portfolio/{domain}/nameservers` setting `ns1=athena.dns-parking.com, ns2=apollo.dns-parking.com`. Likely cause: Netlify dashboard's "Use Netlify DNS" or a similar one-click that flips the registered NS at the registrar level. **If you ever see SERVFAIL on a Hostinger-registered domain, check `gh api … /portfolio/{domain}` for the `name_servers` field first.**
- **Workbox `autoUpdate` doesn't always pick up new SW within a session**: after shipping multiple builds, some users get stuck on a stale precache. M1.7 polish added an `<UpdateBanner />` that polls `registration.update()` every 60s and surfaces a "Reload" pill when `needRefresh` flips.
- **Don't force-redirect the alias hostnames**: keeping `sveska.netlify.app` (and `*.kineticgain.com`) reachable means we have a live backup when the canonical breaks (e.g. NS drift above). Canonical is enforced via `<link rel="canonical">` in `index.html`, not via 301. Only `www.sveska.studio` is force-redirected (apex preference).
- **Every modal store must be reset in `test-setup.ts` afterEach**: Zustand singletons survive `cleanup()`. A modal left `open=true` by one test will be `open=true` when the next test mounts `<App />`, and its open-effect will fire against the _previous_ test's bootstrapped note id — silently loading the wrong data. The user-click that should open it is then a no-op (deps unchanged). Add a `useFooModal.setState({ open: false })` line for every new `*ModalStore` you ship.
- **jsdom's Blob lacks both `.text()` and `.arrayBuffer()`**: tests that read export Blobs must use a FileReader-based helper (`fr.readAsText(blob)`). See `src/__tests__/export.test.tsx#blobText` for the pattern — markdown.test.tsx reused it after I burned 5 min discovering arrayBuffer also missing.
- **Markdown bundle = +56KB gzip (T3.2)**: markdown-it (~45KB) + dompurify (~11KB) live in the main bundle. Total JS gzip jumped 104→160 KB; still under the 180 KB budget but tight. If M3 closes near budget, lazy-load `@/markdown/render` behind `import()` so plain-text users don't pay for the parser.
- **check-bundle counts only initial-load chunks (T3.7)**: jsPDF is ~125KB gzip (plus html2canvas ~47KB + es helpers ~50KB = 223KB total). `scripts/check-bundle.mjs` parses dist/index.html and only sums assets it references, so `import('jspdf')` chunks don't count against the 180KB budget. Apply the same pattern for any future heavy vendor (Excalidraw at M5, anything M4 brings).
- **Edge functions are NOT lint-checked by SPA tsconfig**: `functions/` (CF Pages, Workers runtime) is bundled by CF, not Vite. It IS typechecked via a separate `tsconfig.functions.json` referencing `@cloudflare/workers-types`. Added to ESLint ignores; review function files in-PR carefully since the lint gate doesn't cover them. _Historical: M0–M6 used `netlify/edge-functions/` (Deno) — same exclusion pattern._
- **check-no-keys catches env-var NAMES too (T4.2)**: the gate's `/\bANTHROPIC_API_KEY\b/` regex flags any occurrence of the literal name, not just shaped values. Burned 5 min when the slash AI's "AI offline — set `ANTHROPIC_API_KEY` in env" toast made the build fail. Fix: keep client-facing copy generic ("see src/ai/README.md") and let the README hold the env-var instructions.
- **Netlify → Cloudflare Pages migration (2026-05-17)**: Netlify free-tier credit cap exceeded mid-M6 (team "fknmiz", `JSONHTTPError: Forbidden` on the `netlify-cli deploy` step). Three escape valves were on the table: stay on Netlify Pro ($19/mo), gate CI to tags only, or migrate. **Picked migration** — same architecture (static + edge function), CF free tier ~10× the headroom. Mechanical delta: `Deno.env.get` → `env.X` parameter (Workers runtime), `context.ip` → `cf-connecting-ip` header, `netlify.toml [[headers]]` → `public/_headers`, `netlify.toml [[redirects]]` → `public/_redirects`. CI workflow switched from `netlify-cli` to **CF Pages git integration** (no `wrangler-action`, no CF API token in GH secrets — CF reads pushes directly). `deploy.yml` renamed to CI; runs only typecheck/lint/test/build gates. Wrangler was added briefly as a dev dep then removed (its Node ≥22 engine req blocked the CF Node-20 runner). `@cloudflare/workers-types` kept for typechecking `functions/api/ai.ts` via `tsconfig.functions.json`.
- **Custom domain attached (2026-05-18, the day after the migration)**: User wanted the branded URL to actually serve, not just redirect. Did the CF nameserver migration end-to-end via API in ~15 min wall-time: added zone via CF API → flipped Hostinger registrar NS via Hostinger API → polled CF until zone activated (3 min) → attached `sveska.studio` + `www.sveska.studio` to Pages project → manually created CNAMEs in the new CF zone (`@` and `www` both → `sveska.pages.dev` proxied) since CF Pages domain-attach doesn't auto-create them → SSL provisioned via Google CA → created CF Page Rule for www→apex 301 → deleted orphaned Hostinger URL forwarder + DNS A record via Hostinger API → flipped canonical URL back to `sveska.studio` in index.html / sitemap / robots / README / GH repo homepage. Only credential the user had to provide was a CF API token (saved at `~/.cf_token`); everything else (Hostinger DNS + registrar) used the existing token in `~/ftpkred.txt`.
- **@excalidraw/excalidraw fails under jsdom (T5.1)**: vendor pulls roughjs which uses bare `roughjs/bin/rough` imports Node ESM can't resolve. Fix in `vitest.config.ts`: alias `@excalidraw/excalidraw` → `src/__mocks__/excalidraw.ts` (stub renders a `<div data-testid="excalidraw-stub">`). Production builds use the real vendor via lazy `import()`. **Pattern applies to any vendor with deep Node-incompatible transitive imports** (e.g. Mermaid had similar issues historically).
- **role="tablist" can only contain role="tab" children (T7.1c)**: axe's `aria-required-children` + `nested-interactive` rules form a vise — closable tabs naturally want a close button next to each tab activate, but a tab cannot contain interactive descendants and a tablist cannot contain non-tab children. Refactor: use `role="toolbar"` on the bar, sibling `<button>`s for activate/close, `aria-current="page"` on the active tab. Toolbar accepts mixed buttons natively. The functional UX is identical.
- **vitest-axe@0.1 augmentation doesn't reach vitest@2 (T7.1c)**: package augments `Vi.Assertion<T>` but vitest@2 resolves `expect()` matchers via `import('vitest').Assertion`. `toHaveNoViolations` shows up at runtime but TS strict-mode build fails. Fix: tiny `src/test/vitest-axe.d.ts` that re-augments `declare module 'vitest' { interface Assertion … }`. Lint suppressions needed (`@typescript-eslint/no-empty-object-type`, unused `T`).
- **Playwright `waitForFunction` is blocked by strict CSP (T7.1b)**: our `script-src 'self'` forbids `unsafe-eval`, and Playwright's predicate evaluator uses eval under the hood. Use CSS-selector waits (`waitForSelector`) instead. Same applies to `evaluate(() => …)` when the predicate runs via Runtime.evaluate — usually fine if it doesn't construct functions from strings.
- **Vite preview on Windows binds to ::1 only (T7.1b)**: `connect(port, '127.0.0.1')` rejects ECONNREFUSED even though `localhost` works. Probe both stacks via `Promise.any` of `tryConnect(port, '127.0.0.1')` + `tryConnect(port, '::1')`. The actual page navigation via Chromium uses `localhost`, which resolves either way.
- **`frame-ancestors` in CSP meta is ignored by browsers (T7.1d)**: directive only works in HTTP headers. Our `public/_headers` ships it as a header on CF Pages — the meta version is belt + suspenders for hosts that strip headers. The browser warning is benign and gets filtered out of the e2e console-error check.
- **CF Pages `_redirects` quirks (post-migration)**: CF's parser rejects absolute-URL redirects (`https://www.x.com/* https://x.com/:splat 301!` → "Only relative URLs allowed") and warns "Infinite loop detected — ignored" on the standard SPA fallback `/* /index.html 200`. The SPA fallback warning is cosmetic — CF Pages auto-serves `index.html` for unmatched routes when it exists at output root, so deep links like `/glossary` and `/pricing` work despite the warning. The www→apex absolute-URL redirect that CF rejected would need to be a Cloudflare zone-level Bulk Redirect rule, which is moot until the custom-domain attach happens.
- **Hostinger URL forwarder requires DNS handoff (2026-05-17)**: Setting up `sveska.studio → https://sveska.pages.dev` in the Hostinger Redirects tab DID NOT automatically update the apex A record from Netlify's IP (75.2.60.5) to Hostinger's forwarding server (2.57.91.91). Had to manually delete the old A record (then Hostinger created the correct one) AND delete the AAAA record (Hostinger left it pointing at Netlify's IPv6 `2a02:4780:84::32`, which caused IPv6-preferred mobile clients to bypass the redirect entirely). After both deletions: IPv4 + IPv6 both follow the 301 chain correctly. **Lesson**: when wiring Hostinger URL forwarding, audit BOTH A and AAAA records — don't trust the redirect UI to handle DNS for you.
- **Hostinger has an AI assistant called Kodee** that can edit DNS records when you give it explicit confirmation. Useful for bulk DNS changes across multiple Hostinger-managed domains in a single prompt — handled the post-migration cleanup (delete sveska.studio AAAA + 2 stale kineticgain aliases) in one round.
- **CF Pages domain attach via API doesn't auto-create DNS records (2026-05-18)**: `POST /accounts/{id}/pages/projects/{name}/domains` succeeds + marks the domain "initializing" but won't create the necessary CNAME in the CF zone. Have to follow up with `POST /zones/{id}/dns_records` manually (apex: `CNAME @ → sveska.pages.dev proxied=true`, www: `CNAME www → sveska.pages.dev proxied=true`). After both DNS records exist, domain status flips to "active" within ~60s with SSL provisioned. Dashboard flow handles this automatically — API doesn't.
- **manualChunks for markdown-it: raw savings ≫ gzip savings (2026-05-27)**: Adding a `manualChunks` rule that pins `markdown-it` + `dompurify` + transitive helpers (`entities`, `mdurl`, `linkify-it`, `uc.micro`, `punycode.js`) into a dedicated `markdown-async-*.js` chunk dropped the initial JS raw bytes 521 → 392 KB (-129 KB) but only saved 0.66 KB gzip (179.78 → 179.12 KB). The reason: markdown-it's HTML-entity tables are extraordinarily compressible (massive token repetition), so gzip's deflate finds them ~99% redundant in the original bundle context too. The real win is parse-time / TTI / PWA-precache size — none of which the bundle gate measures. **Lesson**: don't size-estimate gzip savings from raw module size. Multiply by 0.05–0.2 for entity-heavy libs; the bundle gate underreports the real benefit.
- **CF Single Redirects API needs Account Ruleset perm, but Page Rules works with Zone:Edit alone (2026-05-18)**: When setting up www→apex redirect on sveska.studio, the modern `POST /zones/{id}/rulesets` returned "Authentication error" because the CF API token didn't have Account Rulesets:Edit. The deprecated Page Rules API (`POST /zones/{id}/pagerules`) works fine with just Zone:Edit. Free plan allows 3 page rules. Pattern: `targets: url matches "www.sveska.studio/*"`, action `forwarding_url status 301` to `https://sveska.studio/$1`.
- **Rich editor (CodeMirror 6) — `richEditor` pref, now DEFAULT ON (2026-05-18, "big lift" increments 1+2)**: `src/editor/RichEditor.tsx` (CM6 EditorView) + `src/editor/richImageWidget.ts` (inline image ViewPlugin) + `src/editor/cmExtensions.ts` (slash/snippet/typewriter/sounds). Renders pasted `![](sveska-img:id)` refs as inline `<img>` (data: URI) when the cursor isn't on that ref's line — `Decoration.replace` widget, suppressed on cursor-overlap so it stays editable. Async data-URI resolution caches module-level + dispatches an annotation-only transaction to rebuild decorations (terminates). **Increment 2 ported all M3 power features:** slash commands (via `@codemirror/autocomplete`, reusing getSlashContext + command catalog + fuzzy), snippet expand (updateListener + findTriggerAt, guarded by an annotation against re-trigger), find/replace (`@codemirror/search`, Ctrl+F — UX differs from the textarea's FindReplaceBar), typewriter scroll + typing sounds (updateListener/domEventHandler reading prefs live from the zustand store). **CM stays a dynamic-import chunk (~190 KB lazy) even when default-on, so the 180 KB initial budget holds** — the flip cost is just a brief "Loading editor…" on cold load (SW caches it after). Classic textarea is the opt-out (`richEditor: false`). The textarea path keeps its own hooks (useSnippetExpand, useTypewriterScroll, useTypingSounds, SlashCommands, FindReplaceBar) — CM uses the cmExtensions equivalents; they don't share code by design (different runtimes). **Tests: `test-setup.ts` forces `richEditor: false` (store AND Dexie pref, so per-test bootstrapEditorPrefs reads it back false) so the ~30 App-integration tests keep targeting `data-testid="editor-textarea"`; CM doesn't render meaningfully in jsdom. Driving CM from eval: browser Selection API doesn't map to CM's selection model — use real `paste`/`execCommand('insertText')` events on `.cm-content`.**
- **PWA Service Worker survives origin migrations (2026-05-18)**: User reported sveska.studio showed an old M5-era build (no Blog/Changelog/Pricing in header, no typewriter/sounds in Prefs) even after Hostinger 301 redirect was confirmed working at the DNS/HTTP level. Cause: a Service Worker registered earlier on the `sveska.studio` origin (when it served the Netlify build) was intercepting `fetch` events client-side BEFORE the request hit DNS, serving the cached stale assets. SWs are origin-scoped, so the new SW on `sveska.pages.dev` doesn't replace the old one on `sveska.studio` — and we can no longer push a self-unregistering SW to sveska.studio because nothing deploys there. **Fix path**: user must clear site data + unregister SW on sveska.studio manually (Chrome DevTools → Application → Storage → Clear site data, or mobile Site Settings → Clear & reset). After clearing, the 301 fires properly and they hit the current CF Pages build. **Lesson for future migrations**: when changing a domain's destination, expect installed PWAs on the old origin to keep serving stale content until users actively clear their site data. The proper preventive fix is to push a final "unregister.js" SW to the old origin BEFORE flipping DNS — too late for this migration since the Netlify deploys are frozen.
- **`parseChecklist('')` returns `[{passthrough, ''}]`, not `[]` (2026-07-01, extension build)**: `''.split('\n')` returns `['']` (one empty element), which the parser turns into one empty passthrough at index 0. For a fresh Tasks list, this pushed the first appended task to parsed-index 1 instead of 0, so the DOM data-testid was `task-checkbox-1` not `task-checkbox-0` — a subtle UI bug caught only by an integration test. Fix in `extension/src/lib/checklist.ts`: early-return `[]` for empty body. **Deliberate divergence from the PWA's parser** (kept in a comment). Consider back-porting if the PWA ever adds a create-empty-checklist path.
- **PWA vitest picks up `extension/tests/*` unless excluded (2026-07-01)**: extension shipped as a sibling package with its OWN vitest config, but the PWA's root `vitest.config.ts` uses the default include (`**/*.test.{ts,tsx}`) which reaches into `extension/tests/`. Running the PWA suite failed with "Cannot read properties of null (reading 'useState')" — the classic multiple-React-instances error, because the extension has its own React install and its own chrome.\* shim setup that conflicts with the PWA's jsdom setup. Fix in `vitest.config.ts`: `test.exclude: ['**/node_modules/**', '**/dist/**', 'extension/**']`. **Pattern**: any future sibling package with its own vitest needs the same exclusion added here.
- **MV3 service worker: keep it standalone, no imports (2026-07-01)**: `extension/src/background.ts` deliberately imports NOTHING from other extension files. This keeps it a single-chunk emit (`background.js`, 0.15 KB gzip). If it imported from `../lib/id.ts` or similar, Rollup would emit shared chunks that the SW would need to resolve at runtime via `chrome-extension://<id>/chunks/...` URLs — works in practice but harder to debug in the SW context (no console, DevTools access is per-worker). Rule: **service workers are configuration, not application code.**
- **CF Pages doesn't ship the extension — CF Pages ships only the PWA (2026-07-01)**: build outputs are separate: `pnpm build` at repo root builds the PWA to `dist/` (CF Pages pushes this via git integration); `pnpm build` in `extension/` builds the extension to `extension/dist/` (load-unpacked / Web Store submission surface). CF Pages is configured to build from repo root, so `extension/dist/` never gets deployed to `sveska.studio` — correct behavior, but worth noting: **the extension has no hosted URL**. Distribution is via Web Store or hand-off of the built `dist/` folder.
- **Extension icons: brand `favicon-16.png` = MV3 `icons/icon-16.png` (2026-07-01)**: the PWA's brand kit at `public/brand/icons/` has `icon-48.png` and `icon-128.png` but no `icon-16.png` — the small size lives as `favicon-16.png`. The extension needs 16/48/128 (Chrome's expected sizes for MV3), so the initial copy renamed `favicon-16.png` → `icon-16.png` inside `extension/public/icons/`. If a proper `icon-16.png` gets added to the brand kit later, update `extension/public/icons/` and drop the rename.
- **Theme system extended with named accents + density presets (2026-07-01, Phase 2)**: `public/brand/tokens.css` gained 3 named themes (`charcoal`, `midnight`, `sepia`) and 3 density presets (`compact` / `comfortable` / `spacious`), all additive — existing dark/light behavior is unchanged, all changes are new `data-theme=...` / `data-density=...` selectors. Bundle delta: initial JS 124.58 → 125.13 KB gzip (+0.55 KB for the store + modal additions), CSS 8.41 → 8.72 KB gzip (+0.31 KB for the new theme/density selectors). Total 133.86 / 180 KB — plenty of headroom.
- **Sibling `/extension` package added — Chrome side panel (2026-07-01, Phase 1)**: full package at `extension/`, MV3, sidePanel + storage permissions only. Bundle: 48.23 KB gzip JS + 1.99 KB gzip CSS = ~50 KB total, ~40% of the PWA. ## Workflow preferences (user)

- **Externalized state**: 90%+ of context lives in `CLAUDE.md` / `tasks.md` / `plan.md` / `memory.md`. New sessions read these 4 files, ignore conversation history older than current session.
- **Phased work**: Plan → ticket → verify → commit → checkpoint (suggest `/compact`) → next ticket.
- **Subagents**: Use for parallel file exploration to avoid bloating the main context. Don't grep yourself if a subagent can do it.
- **Critical-info-at-edges**: front of the conversation = mission; end of the conversation = current ticket. Middle decays.

## Workspace + organization build (2026-07-29)

- **Dexie v3** adds `directories` and a nullable `notes.directoryId`. Directories form a nested adjacency list through `parentId`; deleting a subtree moves affected notes to the unfiled root instead of deleting content.
- **Ultrawide behavior** is a persisted `workspaceWidth` preference with `reading`, `wide`, and `full` modes. `full` is the default because it matches the requested 37-inch workspace; reading and wide remain one-click constraints. The editor route owns the viewport-height workspace while content routes retain their document flow.
- **Tabs wrap** into bounded chips instead of using horizontal overflow. The no-scrollbar requirement is deliberate because hidden off-screen tabs are a navigation failure, not a styling nuisance.
- **Markdown workspace** now has explicit Edit, Split, and Preview views. Table insertion is a shared command that writes valid Markdown at the current selection and is available from both the note toolbar and command palette.
- **Built-in template seeding uses `put` with stable IDs.** A check-then-add implementation was only sequentially idempotent and could throw `ConstraintError` when two app shells mounted concurrently.
